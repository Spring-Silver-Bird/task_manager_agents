# AGENTS.md

## 1. Назначение

Единая инструкция для AI-агентов, работающих с этим репозиторием.
`README.md` — документация для людей, `AGENTS.md` — рабочие правила агента.

При конфликте требований приоритет такой:
безопасность → существующие тесты → стиль проекта → удобство.

## 2. О проекте

Django-монолит «Менеджер задач».

- Python: >= 3.12 (источник истины — `pyproject.toml`).
- Django: >= 6.1.
- Локальная БД: SQLite; production: PostgreSQL через `DATABASE_URL`.
- Статика: WhiteNoise; CSS: django-tailwind-cli.
- Фильтрация: django-filter; ошибки: Sentry.
- UI и сообщения — на русском; код и идентификаторы — на английском.

## 3. Источники истины

- `pyproject.toml` — зависимости, настройки ruff, pytest, coverage.
- `Makefile` — основные команды.
- `task_manager/settings.py` — конфигурация.
- `task_manager/urls.py` и `<app>/urls.py` — маршруты и namespaces.
- Существующие тесты — зафиксированное поведение.

## 4. Быстрый старт

```bash
cp .env.example .env
make setup
uv run python manage.py runserver
```

Перед запуском заполнить `.env` реальными локальными значениями.
Секреты production задаются в Render Dashboard, а не в репозитории.

Переменные окружения:

- `SECRET_KEY` — обязательна в production, не коммитить.
- `DEBUG=True` — только локально.
- `DATABASE_URL` — обязательна в production.
- `SENTRY_DSN` — опционально.
- `ALLOWED_HOSTS` — список хостов через запятую.
- `CSRF_TRUSTED_ORIGINS` — список origin через запятую.
- `DJANGO_SUPERUSER_USERNAME`, `DJANGO_SUPERUSER_EMAIL`, `DJANGO_SUPERUSER_PASSWORD` — только для bootstrap-создания суперпользователя.

## 5. Команды

| Команда | Назначение |
|---|---|
| `make install` | `uv sync --dev` |
| `make setup` | установка зависимостей и миграции |
| `make migrate` | применить миграции |
| `make tailwind-build` | собрать CSS |
| `make collectstatic` | собрать статику |
| `make lint` | `ruff check` + `ruff format --check` |
| `make tests` | pytest + coverage, порог 80% |
| `make superuser` | создать суперпользователя из env |
| `make render-start` | запуск gunicorn |
| `uv run python manage.py check --deploy` | проверка production-настроек |
| `uv run python manage.py makemigrations` | новые миграции |

## 6. Карта репозитория

- `task_manager/` — настройки проекта, корневые views, urls, wsgi/asgi.
- `task_manager/users/` — регистрация, список, изменение и удаление пользователей.
- `task_manager/statuses/` — CRUD статусов.
- `task_manager/labels/` — CRUD меток.
- `task_manager/tasks/` — задачи, формы, фильтры, admin.
- `task_manager/templates/<app>/` — шаблоны приложений.
- `task_manager/tests/` — тесты Django TestCase/pytest.
- `assets/images/` — статические изображения.
- `tailwind/tailwind.css` — входной файл Tailwind.
- `.github/workflows/` — CI.

## 7. Архитектурные правила

- Использовать class-based views в стиле текущего проекта.
- URL-маршруты подключать через namespaces: `users`, `statuses`, `labels`, `tasks`.
- Формы хранить в `<app>/forms.py`; фильтры — в `<app>/filters.py`.
- Бизнес-логику не размещать в шаблонах.
- Для списков и деталей использовать `select_related`/`prefetch_related`.
- Новые зависимости добавлять только после согласования, с объяснением.
- Миграции создавать через `makemigrations`; применённые миграции не редактировать.
- Не менять URL-имена, namespaces и правила доступа без согласования: на них завязаны тесты Hexlet.

## 8. Текущие правила доступа

- Удалять задачу может только её автор.
- Изменять и удалять пользователя может только сам пользователь.
- Статусы и метки может изменять любой авторизованный пользователь — по текущей спецификации.
- Задачи, статусы, метки доступны только авторизованным.
- Любое изменение правил доступа сопровождать тестами.

## 9. Admin-политика

- Admin — отдельная moderation-поверхность с полным доступом суперпользователя.
- Это осознанное решение: superuser может удалять задачи, статусы и метки через `/admin/` в обход правил приложения.
- Superuser не является заменой проверкам прав в обычном UI.
- Нельзя автоматически создавать superuser в `build.sh`, миграциях или при старте приложения.
- Bootstrap-суперпользователь создаётся вручную через `make superuser`, пароль хранится только в `.env` или менеджере паролей.
- Для обычных модераторов использовать staff + permissions, а не общий superuser.
- Изменения в admin сопровождать тестами.

## 10. Код и шаблоны

- Соблюдать ruff: line-length 120, правила E/F/I/W.
- Не добавлять комментарии без запроса.
- Сохранять существующий стиль CBV, сообщений и шаблонов.
- Новые строки UI — на русском; `verbose_name`/`gettext_lazy` — как в моделях.
- Не выполнять массовое форматирование и несвязанные рефакторинги.
- Не использовать `|safe` и raw SQL без крайней необходимости.

## 11. Тесты

- Каждое изменение поведения сопровождать тестом.
- Использовать `reverse()`, `force_login()`, `assertRedirects()`.
- Проверять и успешные, и запрещённые сценарии.
- Не снижать порог coverage и не удалять тесты ради прохождения CI.
- Для изменений безопасности добавлять регрессионные тесты.
- Перед завершением задачи: `make lint && make tests`.

## 12. Безопасность

- Секреты только через env; `.env`, `db.sqlite3`, `staticfiles` не коммитить.
- В репозитории допустим только `.env.example` с placeholder-значениями.
- Не допускать production-fallback для `SECRET_KEY`.
- `DEBUG` не включать в production.
- `ALLOWED_HOSTS` должен быть явным; не использовать wildcard-домены.
- Sentry: не отправлять PII, cookies и тела запросов.
- Сохранять CSRF, security middleware и logout только через POST.
- Права проверять на сервере, а не скрытием кнопок в шаблоне.
- Не ослаблять валидаторы паролей и настройки HTTPS без согласования.
- После изменения settings запускать `check --deploy`.

## 13. Рабочий процесс агента

1. Прочитать `AGENTS.md`, `README.md` и относящиеся к задаче файлы.
2. Проверить `git status` и не трогать чужие незакоммиченные изменения.
3. Для задач из 3+ шагов составить todo-план.
4. Делать минимальный диф; не менять несвязанный код.
5. Запустить `make lint` и `make tests`; для settings — `check --deploy`.
6. Сообщить изменённые файлы, команды проверки и остаточные риски.
7. Коммиты, push и PR — только по явному запросу.

## 14. Definition of Done

- [ ] Поведение соответствует задаче.
- [ ] Добавлены/обновлены тесты.
- [ ] `make lint` проходит.
- [ ] `make tests` проходит, coverage >= 80%.
- [ ] Нет секретов и отладочных изменений в диффе.
- [ ] Для settings выполнен `check --deploy`.
- [ ] Документация обновлена, если изменились команды или env.

## 15. Запреты

- Не редактировать `.github/workflows/hexlet-check.yml`.
- Не коммитить `.env`, `db.sqlite3`, `staticfiles`, `.venv`.
- Не отключать тесты, CSRF, проверки прав и валидаторы ради зелёного CI.
- Не делать force-push и не переписывать историю.
- Не добавлять тяжёлые зависимости без согласования.

## 16. Известный техдолг

- Sentry отправляет PII и тела запросов.
- Есть fallback `SECRET_KEY` в `settings.py`.
- Нет production-настроек HTTPS/cookies/HSTS и `SECURE_PROXY_SSL_HEADER`.
- Нет rate limiting для login/регистрации и admin.
- Смена пароля не требует текущего пароля.
- Dev-зависимости смешаны с runtime.
- gunicorn в Makefile без привязки к `$PORT`.
- Мелкие баги шаблонов и N+1 в задачах.
